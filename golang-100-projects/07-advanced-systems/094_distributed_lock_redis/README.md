# Project 094 — Distributed Lock with Redis

## 1. Project Name and Number

- Project 094, `094_distributed_lock_redis`.
- The folder name is fixed by the curriculum table; do not rename the directory.

## 2. Project Idea

A single-Redis lease lock. Acquire is an atomic `SET key value NX PX <ttl>` that writes a cryptographically random ownership token only if the key is absent, with a positive bounded time-to-live and a cryptographic token length. Release is a server-side script that compares the stored value to the caller's token and deletes the key only on a match, so a non-owner or a stale owner cannot release. Acquire waits with a bounded deadline and an injected backoff, jitter, clock, and sleeper so the unit tests never sleep. The required scope is acquire plus release, with an injected token source. The token is an absolute secret: it is never logged at any level including debug, and an opaque lock handle privately retains key and token for release without exposing token bytes through exported fields.

## 3. Why This Project Now?

- This project is the cross-process coordination capstone for the early database and concurrency work.
- It pulls the discipline of "validate, then commit" into a single-instance lease lock and forces honest accounting of what a single Redis can and cannot promise.
- The previous project pulled together tokenization, parsing, and first-error semantics; this project pulls together atomic Redis primitives and the limits of single-node coordination.
- The formal prerequisites — project 041 (context cancellation example), project 065 (Redis caching layer), and project 066 (database transaction manager) — each contribute one ingredient that this lock combines.

## 5. What You Must Know Before Starting

- That `SET key value NX PX <ttl>` is a single atomic operation: either the key is created with the value and the TTL, or the operation fails because the key exists. There is no window between "key is absent" and "key is set".
- That a TTL is a hint to Redis about when the key may be evicted; a long client pause can outlive the lease, and the client must treat the lease as lost when it returns from a pause.
- That `DEL` alone is insufficient for release because a non-owner could delete someone else's lock; release must compare the stored value to the caller's token and delete only on match.
- That a Redis Lua script runs atomically with respect to other commands on the same shard, so the compare-and-delete is race-free.
- That tokens must be cryptographically random at a length that makes guessing infeasible.
- That backoff with jitter is the right shape for contended acquire because uniform backoff synchronizes clients.
- That "exactly-once" is a property of an algorithm plus its downstream consumer; this lock is not exactly-once on its own.
- That a fencing token is a monotonic value issued by a serial authority; this lock is not a fencing token and must not be described as one.

## 6. Explanation of New Concepts

### Concepts

- Ownership token as a capability, kept absolutely secret: the value stored under the lock key is the capability. The capability is generated by the client and is opaque to Redis. The capability is the only thing the client needs to release the lock; if the client loses the capability, it cannot release the lock, which is the correct outcome. The token is never logged at any level including debug; the lock handle keeps the token privately and exposes no exported token field; there is no API that returns the token bytes to the caller.
- Atomic acquire with TTL: `SET key value NX PX <ttl>` writes the value only if the key is absent and sets the expiry in one atomic step. The TTL is mandatory and is positive and bounded.
- Atomic release with compare-and-delete: the release is a Lua script that reads the stored value, compares it to the caller's token, and deletes the key only on match. The script returns whether a deletion happened.
- Pinned acquire outcomes: `Acquired`, `NotAcquired` after the bounded attempts without a Redis error, `Canceled` or `DeadlineExceeded` from the caller's context, `TokenGenerationFailure` if the injected source fails to produce a usable token, and `RedisError` for any Redis-side failure. A `RedisError` is never silently mapped to `NotAcquired`. The two are distinct typed outcomes.
- Pinned release outcomes: `Released` on match and delete, `NotOwner` for absent or mismatched token, `Canceled` or `DeadlineExceeded` from the caller's context, and `RedisError` for any Redis-side failure. A `RedisError` or cancellation leaves the release outcome unknown; the implementation never claims ownership was lost and never claims the release occurred.
- Bounded acquire wait with injected primitives: acquire polls Redis with an injected backoff policy, jitter, clock, and sleeper. No real sleep occurs in unit tests.
- Injected token source: the cryptographic source is selected at construction time and injected so the tests can exercise generation behavior including source errors, wrong-length tokens, all-zero tokens, and bounded same-client reuse before any Redis call. Production wiring uses `crypto/rand`; the source length is pinned.
- Context per operation: each acquire and each release uses its own context. A cancel of one operation does not retroactively remove the Redis key, and a release that is canceled before or during the Redis interaction reports the context outcome without claiming `Released` or `NotOwner`.
- Honest limitations: a single Redis is not consensus. A network partition can leave the lock in an ambiguous state. A long pause can outlive the lease, so a client may believe it holds the lock when it does not. There is no fencing token, so a downstream resource cannot distinguish the lock holder from a stale actor. Two clients can therefore act sequentially or overlap from the resource's perspective. The lock is not a substitute for an idempotency key, a database constraint, or a fencing token. The lock is not exactly-once and is not safe for every critical side effect.
- Cross-process collision risk: the cryptographic token length makes cross-process collision negligible but not mathematically impossible. The unit test exercises the deterministic collision behavior of the injected source up to a small pinned generation-attempt bound, after which `TokenGenerationFailure` is reported with no Redis call.

## 8. Functional Requirements

1. The caller supplies a logical lock name of 1 through 64 ASCII letters, digits, periods, underscores, or hyphens. The Redis key is that name under the exact `tutorial-lock:` namespace. Invalid names are rejected before any Redis call. Two clients that use the same logical name contend for the same lock.
2. Acquire writes the caller's ownership token with `SET key token NX PX <ttl>` only if the key is absent. The TTL is from 100 milliseconds through 30 seconds inclusive. The token is exactly 32 random bytes from the injected source. The atomic operation has the documented expiry semantics.
3. Acquire accepts a context with a deadline. Its effective wait ends at the earlier of that deadline and five seconds, and it issues at most eight Redis acquire attempts. It polls with the injected backoff, jitter, clock, and sleeper. Acquire returns `Acquired` when the lock is held by the caller, `NotAcquired` when the wait or attempt bound is reached without a Redis error, `Canceled` or `DeadlineExceeded` when the caller's context is done, `TokenGenerationFailure` when the source cannot produce a usable token, and `RedisError` for any Redis-side failure. `RedisError` is not remapped to `NotAcquired`.
4. Release runs the Lua script that compares the stored value to the caller's token and deletes only on match. Release returns `Released` on match and delete, `NotOwner` for absent or mismatched token, `Canceled` or `DeadlineExceeded` from the caller's context, and `RedisError` for any Redis-side failure. The raw token is never logged or exposed to the caller. The opaque lock handle retains it privately for release.
5. The lock handle exposes no exported token field or token accessor. The raw token bytes do not appear in any returned field, error value, or log line at any level including debug.
6. Each operation uses its own context. A cancel of one operation does not remove the Redis key, and a release canceled before or during the Redis interaction reports the context outcome without claiming `Released` or `NotOwner`.
7. The injected token source is exercised. Source errors, wrong-length tokens, and all-zero tokens cause `TokenGenerationFailure` without any Redis call. A token already issued by the same client is rejected and generation is retried, with at most three generation attempts total. Exhausting those attempts returns `TokenGenerationFailure` without any Redis call. Production still uses `crypto/rand`; cross-process collision is negligible but not mathematically impossible.
8. A graceful close of the client releases no locks; release happens only through the release path. The client may refuse further operations after close.
9. A TTL of zero or negative is rejected by acquire before any Redis call. The key namespace is validated before any Redis call.

## 9. Inputs and Outputs

### Interface Contract

- Acquire input: a validated logical name, a TTL from 100 milliseconds through 30 seconds, a context with a deadline, and the injected backoff, jitter, clock, and sleeper. The operation also enforces the five-second and eight-attempt bounds.
- Acquire output: an opaque lock handle on `Acquired`, or one of the distinct typed outcomes `NotAcquired`, `Canceled`, `DeadlineExceeded`, `TokenGenerationFailure`, `RedisError`. The handle retains key and token privately and exposes no token field.
- Release input: the opaque lock handle.
- Release output: `Released` on match and delete, `NotOwner` for absent or mismatched token, `Canceled` or `DeadlineExceeded` from context, or `RedisError`. The token is never returned.
- Behavior examples:
  - Two clients contend for the same key with TTL one second. One acquires; the other reaches the bounded attempts and returns `NotAcquired`. After expiry, the second client or a third acquires.
  - A client acquires, the network is interrupted longer than the TTL, the client returns, and calls release; release returns `NotOwner`. The implementation does not raise a fatal error.
  - A client acquires, then release is called with a forged token from a different process; release returns `NotOwner`.
  - The injected source produces an all-zero token; acquire returns `TokenGenerationFailure` without any Redis call.

## 10. Rules and Edge Cases

- A TTL of zero or negative is rejected before any Redis call.
- The token source is consulted at most three times; after the third unusable or same-client-reused token, acquire returns `TokenGenerationFailure` with no Redis call.
- `RedisError` and `NotAcquired` are distinct typed outcomes and are not interchangeable.
- A release by a non-owner returns `NotOwner`. The key remains in Redis.
- A release after expiry returns `NotOwner` because the key is absent or has been taken over.
- A release canceled before or during the Redis interaction reports the context outcome; the caller may not assume `Released` or `NotOwner`.
- A cancel of the acquire context reports `Canceled` or `DeadlineExceeded` and never silently succeeds.
- A cancel of an in-flight acquire after the Redis call was issued reports the context outcome with the Redis key and acquire outcome unknown.
- `RedisError` during release reports the typed error and the caller may not assume the lock is released.
- The token source is `crypto/rand` in production. The injected source in tests is allowed to produce deterministic collisions to exercise the bounded retry, after which `TokenGenerationFailure` is returned without any Redis call.

## 11. Project Constraints

- The Redis client version is `go-redis` v9, selected by the learner at implementation time from currently supported patch versions and pinned in the module. No invented patch version appears in the documentation.
- Acquire uses `SET key value NX PX <ttl>`. The `SETNX` followed by `EXPIRE` pattern is forbidden.
- Acquire accepts TTLs only from 100 milliseconds through 30 seconds and stops at the earlier of five seconds, eight Redis attempts, or caller context completion.
- Release is a Lua script, not a client-side `GET` followed by `DEL`. The client-side pattern is forbidden.
- The required scope is acquire plus release. Background auto-renewal and heartbeat goroutines are not core requirements and are not milestones. An optional one-shot renewal may be added in the optional extensions and must compare the token atomically.
- Unit tests must run locally with no Docker and no Redis. They use a fake command and script boundary.
- The optional integration test runs against Redis started in a container, with a build-tag gate and an explicit environment opt-in. Behavior under a short real TTL is exercised with generous polling because timing is real.
- The token source is `crypto/rand` in production; tests inject a source that can be programmed for the bounded retry behavior.
- The unit tests must not perform real sleeps. Backoff, jitter, clock, and sleeper are injected.
- The token bytes never appear in any log line at any level including debug; tests assert this with a log capture helper.
- Token collision behavior is a deterministic unit test, not a probabilistic integration assertion.

## 13. Implementation Milestones

1. Define the opaque lock handle as a value type. The handle retains key and token privately and exposes no exported field for token.
2. Define the Redis boundary interface used by the lock. The boundary exposes the operations the lock needs and nothing else.
3. Implement the injected token source used in tests, plus the production wiring to `crypto/rand`.
4. Implement acquire with `SET NX PX`, the injected backoff and jitter, the injected clock and sleeper, and the pinned outcome set.
5. Implement release as the Lua script read-comparison-delete, with the injected script executor.
6. Implement the typed outcome set: `Acquired`, `NotAcquired`, `Canceled`, `DeadlineExceeded`, `TokenGenerationFailure`, `RedisError`, `Released`, `NotOwner`.
7. Implement the log policy with the absolute secret rule for the token at every level including debug.
8. Write the unit test suite. Tests use the fake boundary and cover every outcome, contention, pause-and-return, source error, wrong-length token, all-zero token, bounded reuse, cancellation before and after the API call, and the token-leak check.
9. Write the opt-in integration test gated by build tag and environment opt-in. The test may use a short real TTL with generous polling. Token collision behavior is not asserted here.

## 14. Verification Cases the Learner Must Write

### Required Cases

- Acquired: a single client acquires with no contention; release succeeds with `Released`.
- NotAcquired: a holder is present; a second client reaches the bounded attempts and receives `NotAcquired`. `NotAcquired` is not a `RedisError`.
- NotOwner: a non-owner release returns `NotOwner`; the key remains in the fake.
- NotOwner after expiry: with the fake clock and TTL the lock expires; a second caller acquires; the first caller's release returns `NotOwner`.
- TokenGenerationFailure: a programmed source error, a wrong-length token, an all-zero token, and bounded same-client reuse each return `TokenGenerationFailure` with no Redis call recorded by the fake.
- RedisError: a fake that returns a transport error yields `RedisError` on acquire and on release. The acquire outcome is not silently remapped to `NotAcquired`.
- Cancellation: cancellation before the API call returns `Canceled` or `DeadlineExceeded` with zero Redis calls; cancellation after the API call is issued returns the context outcome with the Redis key and acquire outcome unknown.
- Secret-keeping: a captured debug-level log line for acquire and release does not contain the token bytes; the handle exposes no exported field that returns the token bytes.
- No real sleep: the unit test runs and finishes without any time-based primitive advancing real time.
- Opt-in integration: with the gating flag and the gating build tag set, a short real TTL expires, contention is exercised, and the daemon-side behavior is observed with generous polling.

## 15. Common Mistakes to Watch For

- Using `SETNX` followed by `EXPIRE`; the two-step pattern is not atomic and is forbidden.
- Using a client-side `GET` followed by `DEL` for release; the window is racy and is forbidden.
- Treating `NotAcquired` as a `RedisError`; the two are distinct typed outcomes.
- Logging the token at any level including debug; the token is an absolute secret.
- Adding auto-renewal or a heartbeat goroutine to the core scope; auto-renewal is out of core and is forbidden from being a core milestone.
- Issuing a fencing token; this project is not that primitive and must not pretend to be.
- Calling the lock "exactly-once"; the lock is a lease, not an exactly-once delivery guarantee.
- Embedding context in the lock handle; context is per operation.
- Returning the token through any API value, error, or log line.
- Letting `RedisError` collapse into a generic "failed" outcome on either side.
- Testing collision probability through the integration test; collision behavior is a deterministic unit test.
- Inventing a Redis client version in the documentation; the learner selects and pins a currently supported version at implementation time.
